## How Vane Data and HawDB divide the work

Vane Data is a multimodal data engine for AI workloads. It provides Python and SQL interfaces for processing images, video, and text and passing them to models.

In this PoC, Vane reads video frames and calls models to extract statements and test conditions from subtitles and images, then assess whether the statements can be compared. The application runs these steps and checks the returned fields and citations against the source material.

Vane represents video frames as rows with timestamps. Model calls accept text and image columns and return structured fields. The application uses column selection and Arrow data exchange to pass data between these steps, then validates the extracted conditions, observations, and references.

HawDB is a multimodal embedded database written in Rust, with Cypher queries and transactional reads and writes. The PoC uses it to store video metadata, subtitles, frame analysis records, source relationships, and processing versions. When semantic search is enabled, it also stores text and vectors and runs similarity queries. HawDB runs locally inside the application, without a separate database service.

Graph queries answer which creator, video, and processing run a record came from. Vector search answers which records relate to the current question. Evidence identifiers connect the two so relevant hits still have a traceable source.

| Stage | What the tools provide | What the application controls |
| --- | --- | --- |
| Frame preparation | Vane returns video frames and timestamps in batches | Sampling interval, dimensions, PNG output, and recognition of frame text |
| Semantic search, optional | FastEmbed generates vectors; HawDB stores text, vectors, and source metadata and runs similarity queries | Chunking, index versions, and candidate passage selection |
| Extraction and comparison | Vane organizes text and image inputs and structured outputs | Candidate material, prompts, field checks, and reference validation |
| Storage and source review | HawDB stores evidence and source relationships and provides transactional reads | Source versions, links from citations to video positions, and caching |

Original videos and extracted PNG files stay on the local filesystem. A Rust program imports subtitle and frame analysis records from JSONL into HawDB. The application saves comparison results as JSON, along with the source versions used.

The code below follows the data from frame reading and storage through retrieval, extraction, and comparison.

## Build a traceable multimodal data flow

### Collect and structure the material

Both A and B have subtitles. The import keeps their original text and start and end times. Videos without subtitles are transcribed with faster-whisper. To read charts and on-screen text, the application samples frames and sends them for image recognition, keeping the frame time and saved image path.

The excerpt reads a frame every five seconds with Vane and saves each as a PNG named by its millisecond timestamp. `video_path` is a local video path, and `output_dir` is an empty directory prepared beforehand. No `frame_limit` is specified here.

```python
from pathlib import Path

from PIL import Image
import vane

con = vane.connect()
height, width = 720, 1280
frames = vane.read_video_frames(
    video_path, image_height=height, image_width=width,
    sample_interval_seconds=5.0,
    connection=con,
)
with frames.select("frame_time", "data").to_arrow_reader(batch_size=4) as reader:
    for batch in reader:
        times = batch.column("frame_time").to_pylist()
        for timestamp, frame in zip(times, batch.column("data"), strict=True):
            pixels = frame.value.values.to_numpy().reshape(height, width, 3)
            path = Path(output_dir) / f"{round(timestamp * 1000)}.png"
            Image.fromarray(pixels).save(path)
```

`frame_time` is in seconds. RGB pixels in `data` are reshaped to the requested dimensions. `batch_size=4` means four frames per batch, not a total frame cap; the API's input-size and decoded-frame safety limits still apply. Later excerpts reuse `con`; call `con.close()` after processing finishes.

Each selected frame is a row in Vane: `frame_time` is the time column, and `data` is the image column. The application selects both and reads pixels in Arrow batches without first collecting every sampled frame from the video.

The image and its timestamp stay in the same row, so later model output can be traced back to a frame time. This example saves PNG files for readers to inspect. Vane handles frame reading, column selection, and batch output.

The application then calls a model through Vane to recognize frame text and records the video source, frame time, and PNG path. These results are stored alongside subtitles for retrieval and comparison. See the [read_video_frames documentation](/docs/data/reference/multimodal-data/video/read-video-frames) for the interface.

Sampling every five seconds can miss a chart that appears briefly. A one- or two-second interval allows closer inspection, at a higher storage and recognition cost. Even then, sampling may miss details.

For example, the system read a frame at 16:48.583 in [Zhong Wenze's video](https://www.bilibili.com/video/BV1ghec66Eau/?t=1008) as showing 4% battery consumption after an iPhone 18 Pro Max recorded 4K120 video for 15 minutes. Reviewing the video revealed a missing condition: the iPhone 17 Pro in the comparison had 98% battery health, while the other three devices had 100%. The saved image makes that omission possible to check. The battery-consumption figure alone cannot establish cooling performance.

### Persist evidence, versions, and source relationships

The application sends subtitle and frame records to a Rust importer for HawDB. Each evidence record stores text or frame analysis results, timestamps, and a content hash. Its `run_id` links it to a processing version, called a Run. The database also records relationships between creators, videos, and clips.

The PoC reads creator, video, and Run records with this Cypher query from `src/corpus.rs`, reformatted here:

```cypher
MATCH (a:Author)-[:PUBLISHED]->(v:Video)-[:PROCESSED]->(r:Run)
RETURN a.payload AS author, v.payload AS video, r.payload AS run
ORDER BY v.id, r.id
LIMIT 1001
```

`PUBLISHED` connects creators to videos, and `PROCESSED` connects videos to runs. The application takes the Run identifiers and reads their evidence:

```cypher
MATCH (e:Evidence)
WHERE e.run_id IN $runs
RETURN e.payload AS payload
ORDER BY e.run_id, e.start_ms, e.id
SKIP $offset LIMIT $limit
```

`$runs` comes from the preceding query; `$offset` and `$limit` control pagination. The graph query establishes provenance, and property filters select evidence from those runs. Both use HawDB's query interface. Each record can then be cited together with its creator, video, and processing version.

When subtitles or sampling settings change, the application creates a new Run and keeps the old versions. Before a comparison, it selects completed runs and reads their evidence by `run_id`. The material from those selected versions forms the source snapshot.

All evidence is read in one HawDB read transaction before retrieval. Each comparison records the source versions it used, so later subtitle updates leave the original evidence available for review.

HawDB's read transaction keeps the source relationships and paginated evidence consistent during the read. Retaining historical versions is the application's responsibility: it decides when to create a Run, how to name it, and how long to keep it.

## From retrieval to structured analysis

### Retrieve and select candidate passages

For each question, the application searches the stored subtitles and frame records. It groups subtitle cues into passages, adds neighboring cues for context, and attaches frames from the same time interval.

Keyword matching uses titles, subtitles, and recognized frame text. With semantic search enabled, FastEmbed turns material and questions into vectors. HawDB stores the text, vectors, and source metadata and executes similarity queries. The application combines keyword and vector scores, selects and ranks candidate passages, and submits material within the model's input budget.

Each processing version has a corresponding search index that can be rebuilt from original records. A search record contains a chunk identifier, text, vector, and source metadata. Subtitle or frame-text chunks retain `evidence_id`, `video_id`, `run_id`, `kind`, and `start_ms`; chunk identifiers combine the evidence identifier with the chunk number, linking hits back to original evidence.

FastEmbed calculates vectors in Python. The Rust importer writes text, vectors, and metadata through HawDB's `SearchDocument`. HawDB handles vector similarity queries and metadata filters, and the application groups hits into video passages.

Without an embedding model, retrieval uses keywords only. The following query illustrates the optional vector-search path, separately from the comparison run discussed later:

```rust
use hawdb::{SearchMode, SearchQueryOptions};
use std::collections::BTreeMap;

let result = index.search_with_options(
    "",
    Some(&query_vector),
    SearchMode::Vector,
    SearchQueryOptions {
        limit: document_count,
        offset: 0,
        rank_window: None,
        fusion_weights: Default::default(),
        metadata_filters: BTreeMap::from([("video_id".into(), video_id)]),
        policy_epoch: None,
    },
)?;
let hits: Vec<_> = result.hits.into_iter()
    .map(|hit| (hit.id, hit.vector_score))
    .collect();
```

`index` contains records for the selected versions. FastEmbed generates and normalizes `query_vector`. The index establishes the data scope, and `video_id` filters the video. `document_count`, the total document count in the index, is used here as the return limit to obtain vector scores for application-side ranking with keyword scores.

`hits` contains chunk identifiers and vector scores. The application looks up the source records and assigns their scores to the corresponding subtitle passages. These become `passages`, each with an identifier, a list of cues, a time range, and associated frames.

This is `SearchMode::Vector`; the application combines keyword and vector scores. Rechunking or changing the embedding model requires rebuilding the corresponding index while original evidence and source relationships can remain.

### Extract structured statements

The application sends relevant passages to a model through Vane and extracts statements separately for each video. Each statement records one observation or assessment, along with test conditions, devices being compared, uncertainties, and a reference to the supporting subtitle cues. Missing information, including a device that cannot be identified, is left empty.

This subtitle example puts `passages` and the question into a request table. The fields are specific to the review scenario and can be changed for other topics. The application configures `model_options` with its provider, model, and execution options; see the [Prompt API](/docs/data/reference/ai/prompt). `con` is the connection created earlier.

The returned `evidence_id` refers to the input passage's `id`. `first_cue` and `last_cue` are one-based cue numbers within that passage, inclusive at both ends. The application uses them to look up the original text and timestamps.

The prompt below translates the Chinese example for readers. A translated prompt may produce different outputs; reproducing the reported run requires its original prompt, model, code, and inputs.

```python
import json
import pyarrow as pa
from pydantic import BaseModel, ConfigDict

class Statement(BaseModel):
    model_config = ConfigDict(extra="forbid")

    evidence_id: str
    first_cue: int
    last_cue: int
    target_model: str | None
    observed_result: str | None
    evaluation: str | None
    comparison_objects: list[str]
    conditions: list[str]
    uncertainties: list[str]

class Statements(BaseModel):
    model_config = ConfigDict(extra="forbid")

    selections: list[Statement]

request = {
    "question": question,
    "passages": [
        {
            "id": passage["id"],
            "cues": [
                [number, cue["text"]]
                for number, cue in enumerate(passage["cues"], start=1)
            ],
        }
        for passage in passages
    ],
}
relation = con.from_arrow(pa.table({
    "text": [json.dumps(request, ensure_ascii=False)],
}))
result = vane.ai.prompt(
    relation, vane.col("text"),
    return_format=Statements,
    system_message=(
        "Extract supported statements relevant to the question, one point per statement. "
        "Preserve the subject, conditions, numeric units, and source uncertainty. "
        "Use only supplied evidence identifiers and locations; do not mix sources. "
        "Set evidence_id to the passage id. Use the passage's subtitle numbers for "
        "first_cue and last_cue, inclusive at both ends. "
        "Return the requested structure, with null or [] for missing information. "
        "Do not add information outside the supplied material."
    ),
    **model_options,
)
extracted = Statements.model_validate(result.select("response").fetchone()[0])
```

`return_format` specifies the output structure. Reading `response` triggers the model call, and the application then checks the result. Video frames are sent separately as image inputs; their identifiers and timestamps locate them in the source video.

`con.from_arrow()` creates the request table, and `vane.col("text")` selects the input column. `vane.ai.prompt()` declares the model call and return structure; the result is read through the table's `response` column. This example puts a group of candidate passages into one request, so the input table has one row.

The full implementation also groups tasks into a table with `task_id`, `text`, and `images`, sends text and image columns together, and collects results by task identifier. Vane provides multimodal column inputs and result reading. Task boundaries, prompts, input budgets, and completeness checks remain under application control.

The fields in `Statements` have specific uses. `conditions` supports comparability checks. `observed_result` and `evaluation` keep observations separate from the creator's assessment. `evidence_id` and the cue numbers locate the cited text. The application can inspect each field, but still has to check its accuracy against the source.

The application checks that each passage identifier belongs to the current input and that the cue range is valid. It then looks up the original text and times, attaches `run_id`, and adds one neighboring cue on each side. A field without source support is removed and recorded as a partial extraction failure.

The original run missed information that was present in the subtitles. Mediastorm mentioned about three minutes of 4K60 recording, which the model left out of the test conditions. Geekerwan gave approximately 44–45°C, which the model failed to extract as an observation. Both omissions matter when comparing the statements, so the original subtitles remain part of the comparison input.

### Validate evidence and comparability

The comparison model considers extracted fields, cited text, and uncertainties together. It must not treat unconfirmed information as fact or invent test conditions.

It first checks devices, metrics, and conditions, recording `comparability`: `comparable` means a direct comparison is supported, `different_conditions` means the devices or key conditions differ, and `unknown` means evidence is insufficient. Missing conditions must not be assumed identical.

It then uses `relation` to classify agreement, conflict, complementary statements, or an undetermined relationship. This is another `vane.ai.prompt()` call with different inputs, instructions, and return structure.

The application checks reference validity, that the statements come from different videos, and that agreement or conflict labels satisfy `comparable`. These are application rules; model judgments still need source review.

The original comparison of A and B returned:

```json
{
  "comparability": "different_conditions",
  "relation": "undetermined"
}
```

The model based its judgment mainly on differences in workload and where heat was observed. It did not identify the specific devices. The Duo and Pro Max distinction was found later by reviewing the source videos; it was absent from the automated result.

Duration matters too. Zhong Wenze shows a 15-minute 4K120 recording test at 16:38–16:59. [He Tongxue](https://www.bilibili.com/video/BV12peP6kEnK/?t=677) compares temperatures after half an hour of 4K120 recording on iPhone 16, 17, and 18 Pro Max at 11:17–11:28. The mode matches, but the duration differs, so their temperatures cannot be compared directly.

## Reuse data when videos are added

Stored subtitles, frames, and source records can be used again. When a fifth video is added, valid caches preserve the extraction results for the original four videos and their six pairwise comparisons. Only the new video and its four comparisons with the existing videos need processing.

> Reuse requires the original question, model configuration, processing protocol, runner, and source versions to remain unchanged, and the earlier results to be complete.

A new question can reuse the material while rerunning retrieval, extraction, and comparison. Changes to models, rules, or source material update the corresponding results while preserving the source versions used by historical comparisons.

The same division of work could be used for questions about course materials, product research, or knowledge drawn from multiple sources. Vane processes the material and calls models; HawDB stores relationships and provenance. The application keeps each analysis linked to the source versions and citations a reader would need to check it.
